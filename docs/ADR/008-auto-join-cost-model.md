# ADR-008：Auto join 的统计代价选择

状态：已实现（Accepted）；后续 ADR-009 增加单表 `WHERE` 谓词下推，过滤后的扫描行数会进入本文的局部成本比较
日期：2026-11-20

## 背景

ADR-007 让 `ANALYZE` 收集并持久化行数、`NULL` 数和列级 NDV，但当时这些统计只用于 `EXPLAIN SELECT` 的展示。`JoinStrategy::Auto` 仍然按“存在等值键就走 hash join”执行，即使两张表都只有两行；这种情况下 hash 的建表、分配和探测开销可能超过直接嵌套循环。

## 决策

1. 只调整 `JoinStrategy::Auto`。显式 `Hash` 和 `NestedLoop` 仍强制走对应路径，供基准和差分测试使用。
2. 仅当参与该次 join 的两侧都有可用统计时启用代价比较；多表 join 时把前一次 join 输出的 NDV 继续传给下一次选择。任一源表没有统计时，`Auto` 保持原来的 hash-by-key 回退。
3. 使用局部行数成本，不引入全局计划搜索：
   - nested loop：`left_rows * right_rows` 次谓词探测；
   - hash join：右表建桶 `right_rows` + 左表探测 `left_rows` + 估算输出 `output_rows`，三者各按一个成本单位计；
   - 输出行数复用 `estimate_join_rows` 的现有启发式估算。
4. 当 `hash_cost <= nested_cost` 时选择 hash，平局保留原来的 hash-by-key 行为；否则选择 nested loop。没有等值键（`CROSS JOIN`、非等值 `ON`、`OR`/表达式键）仍只能 nested loop。
5. 静态 `EXPLAIN SELECT` 用同一估算和规则显示估算下会选的 `HashJoin` 或 `NestedLoop`；`EXPLAIN ANALYZE` 在真实执行时记录每个 join 的选择并显示它，避免实测计划文本和实际路径不一致。
6. 这是单次 join 的局部代价启发式，不是全局优化器：不重排 join 顺序、不比较候选计划、不做列裁剪、不引入索引或统计直方图。ADR-009 之后，内连接/交叉连接的单表 `WHERE` 谓词可以先在扫描阶段减少输入行，再进入本文的成本比较；这不改变“局部启发式”的边界。

## 后果

- 正结果：小表等值 join 可以避开不必要的 hash 建表开销；大表仍选择 hash；执行路径和 `EXPLAIN` 的选择一致；没有统计时行为保持不变。
- 正结果：代价判断只依赖已有 `TRSS` 统计和内存中的当前行数，不需要后台任务或新持久格式。
- 负结果：成本单位是固定的相对权重，不是机器实测代价；没有考虑哈希冲突、字符串哈希成本、行宽、内存压力和倾斜。
- 负结果：统计是手动快照，DML 后统计失效，`Auto` 会退回 hash-by-key，直到重新 `ANALYZE`。
- 负结果：没有 join 顺序搜索和全局计划比较；多表查询仍按 SQL 中的书写顺序执行。

## 被否掉的替代

- **继续总是选 hash**：实现简单，但两行、三行等小表会为建桶付出固定开销，也无法证明统计真的参与了执行决策。
- **总是选 nested loop**：大表等值 join 会退化为笛卡尔级探测，已有基准显示 1024 行时相差约两个数量级。
- **固定行数阈值**：不能反映 NDV 和输出基数，遇到复合键、空表或高度重复键会误判。
- **直接做完整优化器**：当前没有逻辑计划、候选枚举和代价校准；先把单个 join 的选择闭合，再考虑计划层。
- **用采样统计替代精确统计**：当前表规模小，`ANALYZE` 的精确扫描可控；采样会引入随机性和新的格式/误差问题。
