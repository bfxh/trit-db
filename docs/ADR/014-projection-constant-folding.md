# ADR-014：投影常量折叠的安全边界

状态：已实现（Accepted）
日期：2026-11-20

## 背景

ADR-012 在计划入口折叠 `WHERE`、`HAVING`、`GROUP BY`、`ORDER BY` 和 `JOIN ... ON` 中的常量表达式，但刻意跳过 `SELECT` 项，理由是担心未别名常量表达式的输出列标签发生变化。

检查当前 binder 后，这个担心不成立：`SELECT` 项的输出名只有三种来源：

- 有 `AS alias` 时使用 alias；
- 裸列引用使用列名；
- 其他表达式（包括字面量和算术表达式）使用位置名 `col{position}`。

因此 `SELECT 1 + 1` 和 `SELECT 1 + 1 AS two` 折叠成 `Literal(2)` 都不会改变结果列标签；折叠只影响投影求值方式。与此同时，投影中的 `1 + 1` 目前会对每一行重复求值，纯常量没有必要进入执行器。

本切片只把 ADR-012 的折叠范围扩展到 `SELECT` 项，不引入投影下推、公共子表达式消除或表达式重写框架。

## 决策

1. `fold_select` 遍历所有 `SelectItem::Expr`，对每个表达式调用现有 `fold_expr`；`SelectItem::Wildcard` 保持不动。
2. 仍沿用 `fold_expr` / `fold_constant` 的边界：只有不含 `Column` / `Aggregate` 的表达式才尝试 `eval_constant`；成功替换为 `Expr::Literal`，失败保留原表达式，让绑定/执行阶段按原语义报错。
3. 不改变输出列标签：有 alias 的项保留 alias；裸列项仍走列名；无 alias 的常量/算术项仍由 binder 命名为 `col{position}`。
4. 不改变结果行集、列顺序、`ORDER BY`/`GROUP BY` 别名解析或类型检查；折叠只发生在 `SELECT` / `EXPLAIN` 的计划入口，parser 仍保留原始表达式。
5. `EXPLAIN` 的计划文本仍只显示 `Project [name, ...]`，不显示表达式；折叠不会新增计划节点或改变 `Scan` 节点。
6. 明确不做：投影下推、投影表达式公共子表达式提取、常量传播到列引用、`SELECT` 项别名自动生成、聚合输入折叠、把 `SELECT` 项错误提前到规划阶段。

## 后果

- 正结果：`SELECT 1 + 1 AS two FROM t` 的投影表达式变为字面量 `2`，每行不再重复计算常量算术；结果值和 `two` 标签不变。
- 正结果：无别名的 `SELECT 1 + 1, id FROM t` 仍输出 `col1, id`，列标签不变；常量列每行都是 `2`。
- 正结果：`SELECT 1 / 0 AS bad FROM t` 的常量求值失败，原表达式保留，仍在执行阶段报 `division by zero`，不会因为折叠吞掉错误。
- 正结果：裸列和聚合项不进入常量求值，列解析、聚合合法性和分组语义不受影响。
- 负结果：常量表达式只折叠一次，但仍在计划入口复制表达式；对超长投影列表会增加一次 AST 遍历，收益主要体现在每行求值减少。
- 负结果：折叠不会改变标签，但也不会把无 alias 表达式自动命名为原始表达式文本；输出仍是 `colN`，这是当前 binder 的既有约定。
- 负结果：投影仍是逐行构造，未做投影下推或批量求值；本切片不改善宽行/大结果集的物化成本。
- 负结果：如果未来修改 binder 的命名规则，使未别名表达式按表达式文本命名，本决策需要重新评估；当前测试固定了 `col1` 行为。

## 被否掉的替代

- **继续跳过 `SELECT` 项**：当前 binder 的 `colN` 命名已经消除标签风险；跳过只会保留每行重复求值。
- **只折叠带 alias 的投影项**：无 alias 常量项同样安全且更常见，限制没有收益。
- **为无 alias 常量项生成表达式文本 alias**：会改变现有 `colN` 输出标签，属于破坏性行为，不在本切片做。
- **做完整投影下推/公共子表达式消除**：需要跨计划节点传播列需求和表达式等价判断，范围大于本切片；先闭合纯常量投影。
