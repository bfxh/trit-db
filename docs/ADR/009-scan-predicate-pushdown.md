# ADR-009：单表 WHERE 谓词下推到扫描

状态：已实现（Accepted）；后续 ADR-010 将其扩展为顶层 `AND` 合取项拆分与分别下推，下文保留本切片当时的整条谓词范围
日期：2026-11-20

## 背景

当前 `SELECT` 的执行顺序是先把 `FROM` 中所有源表物化成 join 结果，再在完整 join schema 上绑定并执行 `WHERE`。对于 `SELECT ... FROM a JOIN b ON ... WHERE a.id = 2` 这类只过滤单张源表的查询，这意味着即使左表只有少量行满足条件，仍会先构造完整的 join 中间结果，再把它全部丢掉。

`ANALYZE` 统计和 `Auto` join 成本选择已经能改变 join 算法，但还没有改变“join 前输入有多少行”这一层。先把单表谓词下移到扫描阶段，是一个不依赖索引、也不引入全局计划搜索的局部优化。

## 决策

1. 只处理 **整条 `WHERE` 谓词** 都只引用一个源表、并且该源表的列全部显式限定（`alias.column` / `table.column`）的情况。
   - 谓词中只要出现一个未限定列，就不下推；未限定列的归属由完整 schema 的 binder 决定，提前下推可能改变歧义判定。
   - 谓词引用两个及以上源表时不下推。
2. 只对 **`INNER` / `CROSS` join 链** 下推。`LEFT` / `RIGHT` / `FULL` join 不下推，因为跨外连接移动谓词可能改变未匹配行的保留语义。
3. `WHERE` 被下推后，从最终 `bind_select` 的过滤条件中移除；它在源表扫描阶段用该源表的限定 schema 绑定并逐行求值。最终结果与“先 join 再 WHERE”在内连接/交叉连接上等价。
4. 静态 `EXPLAIN SELECT` 与 `EXPLAIN ANALYZE` 都用 `Scan <label> filtered` 标记被下推的扫描；此时不再生成单独的 `Filter` 节点。若仍有未下推的残余条件，`Filter` 节点继续显示在 join 之上。
5. 估算路径同步调整：
   - 被过滤的源表扫描行数按现有 `estimate_selectivity` 估算，并作为该次 join 的左侧/右侧输入行数；
   - 后续 join 基数、`Auto` 的局部成本选择、`Filter`/`Project`/`Sort`/`Limit` 估算都使用过滤后的行数。
   因此同一个查询在下推后可能从 `HashJoin` 变为 `NestedLoop`（或相反），静态计划与实测计划仍各自记录自己使用的选择。
6. 不拆分 `AND` 连接的多个合取项，也不做列裁剪、join 重排、常量折叠、索引或直方图；这些留给后续计划层切片。ADR-010 已补上顶层 `AND` 合取项拆分这一层，其余边界仍适用。

## 后果

- 正结果：内连接/交叉连接中只过滤单张表的常见谓词会在 join 前减少输入行，降低中间结果和后续探测成本；结果语义保持不变。
- 正结果：`EXPLAIN` 文本能直接看到 `Scan ... filtered`，`EXPLAIN ANALYZE` 的 `Scan actual rows` 是过滤后的扫描行数，便于区分“扫描过滤”和“join 后过滤”。
- 正结果：`ANALYZE` 统计存在时，过滤后的扫描行数进入现有局部成本模型，使 `Auto` 的选择更贴近实际输入规模。
- 负结果：ADR-009 当时只支持整条谓词下推，不支持 `WHERE a.id = 2 AND b.x = 1` 这样的多源合取拆分；ADR-010 已把顶层合取项分别下推，`OR` 和外连接仍受限。
- 负结果：要求显式限定列；`WHERE id = 2` 即使语义上只可能属于一张表，也不会下推。
- 负结果：外连接不做下推，因此 `LEFT JOIN ... WHERE right.col = ...` 仍按 join 后过滤；这是保守但正确的选择。
- 负结果：计划文本和测试断言会随下推改变；例如原本的 `Filter` 节点可能消失，`HashJoin` 可能因输入行数下降变成 `NestedLoop`。

## 被否掉的替代

- **拆分所有顶层 `AND` 合取项并分别下推**：能覆盖更多查询，但需要把残余谓词重新组合、维护每个合取项的来源集合，并处理 `OR`/`CASE` 中的嵌套条件；ADR-009 先用整条谓词闭合最小语义，后续由 ADR-010 实现顶层 `AND` 拆分。
- **外连接也下推**：`LEFT JOIN` 右侧谓词下推会保留本应被 `WHERE` 丢弃的未匹配左行，必须先把外连接降级为内连接或做更复杂的 null-rejecting 分析；当前不做。
- **下推未限定列**：需要先在完整 schema 上解析归属，再把绑定结果映射回源表；当前 binder 的歧义规则可能因此改变，先要求显式限定。
- **不更新估算和计划文本，只改执行**：会让 `EXPLAIN` 与实际执行路径不一致；当前项目一直要求静态计划和实测计划都能解释执行选择，因此不接受。
- **直接做全局逻辑计划和列裁剪**：范围远大于本切片；先把单表过滤这一层闭合，再进入计划层。
