# ADR-012：常量折叠与安全布尔恒等简化

状态：已实现（Accepted）；后续 ADR-014 把投影中的常量表达式纳入折叠范围
日期：2026-11-20

## 背景

谓词下推、合取拆分和源表列裁剪之后，扫描输入和中间行宽已经下降，但查询文本里仍可能出现完全由字面量组成的条件：

```sql
WHERE 1 = 1
WHERE TRUE
WHERE a.id = 2 AND 1 = 1
WHERE 1 = 0 OR a.id = 2
HAVING 1 = 1
```

这些条件在绑定后才由执行器求值。`1 = 1` 会生成一个永远为真的 `Filter`，`WHERE TRUE` 也会保留独立过滤节点；`x AND TRUE` 还会把恒真项带入下推和选择率估算。对小查询这是可忽略开销，但会让计划文本、估算和实际执行路径多出一层噪声，也不利于后续表达式级优化。

本切片只做保守的常量折叠，不引入表达式重写框架、常量传播、公共子表达式消除或代数等价变换。

## 决策

1. 在 `SELECT` 和 `EXPLAIN` 入口统一调用 `fold_select`，把折叠后的 `Select` 交给下推规划、列裁剪、绑定和执行。折叠只作用于查询计划输入，不修改 parser 生成的 AST。
2. `fold_expr` 递归处理所有表达式变体：`Literal`、`Column`、`IsNull`、`IsTruth`、`Not`、`InList`、`Between`、`Like`、`Case`、`Binary`、`Aggregate`。
3. 只有 `expr_is_constant` 为真的表达式才尝试求值：递归检查后不含任何 `Column` 或 `Aggregate`。求值复用 binder 的 `eval_constant`（空 schema、空行），成功则替换为 `Expr::Literal`；求值失败则保留原表达式，让执行阶段按原语义报错。
4. 折叠范围是 `WHERE`、`HAVING`、`GROUP BY`、`ORDER BY` 和每个 `JOIN ... ON`。本切片暂不折叠 `SELECT` 项；后续 ADR-014 确认 binder 对无 alias 的非列/聚合表达式统一使用 `colN` 命名，折叠不会改变标签，因此已把纯常量投影纳入折叠范围。`SELECT` 项中的列/聚合仍不做常量求值。
5. 只做两侧都安全的布尔恒等：
   - `TRUE AND x` → `x`
   - `x AND TRUE` → `x`
   - `FALSE OR x` → `x`
   - `x OR FALSE` → `x`
6. 不做 `FALSE AND x` → `FALSE`、`TRUE OR x` → `TRUE`。这两个改写会改变右侧表达式是否求值，可能吞掉除零、类型错误或函数副作用；当前执行器没有独立的短路/副作用合同，不能把它们当作纯代数化简。
7. `WHERE` 折叠后为字面 `TRUE` 时直接移除过滤器；`HAVING` 同理。字面 `FALSE` / `NULL` 保留为表达式，仍由执行阶段过滤，以保留三值语义和错误路径；`JOIN ON` 的常量真值保留为条件表达式，由 join 求值。
8. `estimate_selectivity` 增加字面布尔/NULL 规则：`TRUE` 选择率为 1，`FALSE` 和 `NULL` 为 0；其他无统计字面量仍走默认 0.5。这样 `WHERE 1 = 0` 折叠成 `FALSE` 后估算为 0 行，而不是继续显示 0.5 的默认选择率。
9. 本切片不实现：`SELECT` 项折叠、常量传播到列引用、跨表达式公共子表达式消除、`CASE` 分支裁剪、`IN` 列表去重/排序、`BETWEEN` 改写为比较、函数副作用建模、逻辑计划或全局优化器。ADR-014 之后，`SELECT` 项中的纯常量折叠已补上，其余仍未做。

## 后果

- 正结果：`WHERE 1 = 1` 不再生成 `Filter`，`EXPLAIN` 直接显示扫描/投影计划；`WHERE 1 = 0` 保留 `Filter` 但估算为 `est rows=0`，执行返回零行。
- 正结果：`WHERE a.id = 2 AND 1 = 1` 在折叠后与 `WHERE a.id = 2` 使用同一条下推路径，扫描节点可以继续显示 `Scan ... filtered`，不会因为恒真项阻止单源条件下推。
- 正结果：`HAVING 1 = 1` 被移除，分组查询不再生成空的 `Having` 节点。
- 正结果：纯常量表达式只在折叠阶段求值一次；含列/聚合的表达式不进入 `eval_constant`，不会改变 binder 的列解析和聚合合法性检查。
- 负结果：常量求值失败时原表达式保留，计划文本仍显示原条件；错误在真实执行时按原顺序触发，不在 `EXPLAIN` 阶段提前暴露。
- 负结果：`FALSE AND x`、`TRUE OR x` 不做简化，因此仍会保留右侧表达式和其潜在错误；这是有意保守。
- 负结果（本切片当时）：`SELECT` 项中的常量表达式（例如 `SELECT 1 + 2`）不折叠，输出列标签和投影求值行为保持不变；ADR-014 后已把纯常量投影纳入折叠，标签仍为 binder 的 `colN`。
- 负结果：没有常量传播；`WHERE a.id = 1 + 1` 不会改写成 `WHERE a.id = 2`，列裁剪也不会因此减少列。
- 负结果：折叠只发生在 `SELECT` / `EXPLAIN` 路径；`UPDATE` 的 `SET` 表达式和 `WHERE` 仍走原有绑定/求值路径。

## 被否掉的替代

- **把所有常量表达式都折叠成字面量并立即替换**：如果常量求值报错，会在规划阶段改变错误时机；当前只在成功时替换，失败保留原表达式。
- **做 `FALSE AND x` / `TRUE OR x` 的恒等简化**：会跳过右侧求值，改变错误和短路行为；在没有副作用/短路合同前不做。
- **折叠 `SELECT` 项（当时否掉，后被 ADR-014 采纳）**：当时担心未别名表达式的输出列标签由表达式文本/结构决定，提前替换会改变 schema 标签；后续确认 binder 对非列/聚合项统一命名 `colN`，因此纯常量投影可以安全折叠。
- **把常量折叠塞进 parser 或 binder**：parser 应保留原始语法结构，binder 仍负责类型和列解析；当前在 engine 的计划入口做一次局部重写，边界更清晰。
- **引入通用表达式重写器/逻辑计划**：范围大于本切片；先闭合常量、恒真条件和选择率这三个可观测点。
