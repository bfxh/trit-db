# 安全审计：SQL 注入与资源上限（2026-11-22）

范围：`tritdb-pgwire`、`tritdb-sql`、`tritdb-cas`、`tritdb-format`、`tritdb-wal`、
`tritdb-store`、`tritdb-exec`、CLI 的参数与解码路径。

方法：静态搜索（SQL 拼接、未校验的数字/标识符、`read_to_end`、解码边界）+ PoC 测试验证。
修复的每一项都带回归测试；未修复的项记录理由。

## 已修复

### 1. PG 扩展查询参数注入（严重）

`crates/tritdb-pgwire/src/lib.rs` 的 `param_literal` 在 `oid = 20/21/23`（int8/int2/int4）时
直接返回客户端文本：

```rust
20 | 21 | 23 => text.clone(),
```

`Bind` 的 parameter type 由**客户端**声明，于是可以声明 int8 并发送
`1; DROP TABLE t`，`substitute_params` 会把它拼进 SQL，`parse_script` 再执行多语句。

**修复**：int 类型改为 `text.parse::<i64>()`，失败返回 `Protocol` 错误。
**回归测试**：`security_tests::integer_parameter_values_must_be_numbers`。

### 2. COPY 表名/列名注入（严重）

`parse_copy` 只做 `trim_matches('"')`，不校验内容：

```rust
let table = head[..open].trim().trim_matches('"').to_ascii_lowercase();
```

`COPY t; DROP TABLE x FROM STDIN` 会得到 `table = "t; drop table x"`，随后
`format!("SELECT ... FROM {table}")` / `format!("INSERT INTO {table} ...")` 被
`execute_script` 当作多语句执行。

**修复**：新增 `is_plain_identifier`（字母、数字、下划线、点），表名与列名不满足即
返回 `None`（COPY 不成立，走普通 SQL 路径报错）。
**回归测试**：`security_tests::copy_table_names_cannot_carry_statements`。

### 3. OCSP 响应内存 DoS（中危）

`post_stream` 用 `stream.read_to_end(&mut response)` 读 OCSP 响应，没有大小上限；恶意
responder 可以返回 GB 级数据。

**修复**：`(&mut stream).take(1024 * 1024)`，超过 1 MiB 截断（后续解析会报 malformed）。

### 4. 表解码器的无上限分配（DoS，已修）

`decode_table` 对 `row_count`、`unique_sets` 的数量、每个 unique set 的列数、`checks` 的数量
都没有上限，直接用于 `Vec::with_capacity` / `Vec::push`。损坏或恶意的表值可以触发数十 GiB
分配：fuzz 实测 48 GiB（`51539607552 bytes failed`）与 12 GiB（`12884901888 bytes failed`），
进程直接 abort。

**修复**：`MAX_ROWS = 1 << 20` 与 `MAX_COLUMNS` 上限校验，超限返回 `CorruptTable`
（`too many rows` / `too many unique sets` / `too many unique columns` / `too many checks`）。
**回归**：`crates/tritdb/tests/fuzz_decode.rs`——随机字节、合法表变异与截断各 2000 轮，
所有解码器（storage / CAS manifest+anchor / format / radix）不得 panic 或 abort。

### 5. 认证比较的 constant-time 加固（时序侧信道，低危）

MD5 digest、明文密码与 SCRAM proof 都走 `constant_time_eq`，但该函数在长度不等时**提前
返回**，长度不符与内容不符走不同路径。改为把长度差折入累加器、循环只覆盖较短输入，两条
失败路径不再有可区分的时间差。
**回归**：`security_tests::constant_time_eq_rejects_length_and_value_mismatches`。

### 6. pgwire 连接配额与引擎锁等待超时（资源耗尽，低危）

`serve_with_options` 对 `listener.incoming()` 没有连接上限，每条连接一个线程并共享一把
`Mutex<SqlEngine>`；慢查询会让其他连接无限期阻塞在 `lock_engine`，恶意客户端可以耗尽线程
与内存。
**修复**：`ServerOptions::max_connections`（默认 64，`0` 不限；`AtomicUsize` 计数，超限回
`too many connections` 并关闭）与 `ServerOptions::engine_lock_timeout`（默认 30 s，`0`
表示无限等待；超时回 `ErrorResponse` + `ReadyForQuery`，不再挂死）。CLI 暴露
`--max-connections` 与 `--lock-timeout-ms`。
**回归**：`security_tests::engine_lock_wait_times_out`、
`pgwire_protocol::connection_limit_refuses_extra_clients`。

### 7. 并发检查-使用窗口核验（无缺陷，补回归）

pgwire 每条消息都在 `lock_engine` 内完成解析与执行，事务状态只在连接内维护
（BEGIN/COMMIT 不跨锁），所以唯一约束、自增计数与 CREATE TABLE 的检查-使用窗口都在同一
把锁内。补回归固定这一性质：8 线程并发插入同一唯一键只有 1 个成功、8 次 UPDATE 不丢计数、
读写混合时 COUNT 始终落在合法范围、并发同名 CREATE 只有 1 个成功、8 条 pgwire 连接并发
插入同一键有 7 个收到错误。
**回归**：`crates/tritdb-sql/tests/concurrency.rs`（4 个）、
`pgwire_protocol::concurrent_connections_keep_unique_constraints`。

### 8. graph / ANN / bench 的边界（健壮性，补测试）

`tritdb-exec::graph` 已有维度不匹配与距离溢出测试，但缺：负坐标距离与等距 id 排序、
`k = 0`、`k` 超过点集、query 超过 `MAX_DIMENSIONS`、`MAX_NODES`/`MAX_EDGES` 构造上限、
TRGR/TRPN 头部声明超限（解码前拒绝）、空点集与 `i64` 极值往返、`usize::MAX` 跳数与越界
节点。全部补为回归。
**附带修复**：`tritdb-bench` 的 `ann-knn`/`graph-reach` 之前对超限参数直接 `.expect`
panic；现在校验 `MAX_POINTS`、`MAX_NODES`、`nodes * fanout <= MAX_EDGES`，以退出码 2 并
给出说明。
**回归**：`cargo test -p tritdb-exec graph::tests`（新增 6 个）。

### 9. LIKE 的 `text x pattern` 内存分配（DoS，已修）

`like_matches` 为每次匹配分配 `(text.len() + 1) * (pattern.len() + 1)` 的布尔矩阵。
实测 text = pattern = 1000/2000/4000/8000 分别耗时 14/55/218/890 ms，内存 1/4/16/64 MiB；
增长是严格的二次方。单条查询消息上限 16 MiB，配合表内的长文本可以把这个矩阵推到 TB 级，
进程直接 abort。

**修复**：改为 O(1) 额外空间的贪心匹配（只在最后一个 `%` 上回溯），pattern 上限 64K 字符，
单次求值 1000 万步预算；超限返回 `LikePatternTooLong` / `LikeTooComplex`（SQLSTATE 22023）。
**回归**：`tests::like_rejects_oversized_patterns_and_runaway_backtracking`。

### 10. JOIN 结果没有行数上限（DoS，已修）

`nested_loop_join_rows` / `hash_join_rows` 把整个结果物化，没有任何上限。实测三张 100 行的
表做 `SELECT * FROM a, b, c` 产生 100 万行、595 ms；三张 1000 行的表就是 10 亿行。

**修复**：`MAX_JOIN_ROWS = 1 << 20`，超限返回
`Unsupported("join produces more than ... rows")`。
**回归**：`engine::tests::cross_join_stops_at_the_row_cap`（2000 × 2000 在第 1M 行被拒）。

### 11. `encode_table` / `decode_table` 行数不对称（数据不可读，已修）

`encode_table` 只校验列数，不校验行数；`decode_table` 却拒绝超过 `MAX_ROWS = 1 << 20`
的表。插入 1,048,577 行后编码成功（9.4 MB），读回时报
`CorruptTable { reason: "too many rows" }`——表从此不可读，且写入路径没有任何提示。

**修复**：`encode_table` 在写入前拒绝超过 `MAX_ROWS` 的表，INSERT 直接报错，不再写出
不可读的表值。
**回归**：`storage::tests::encode_rejects_more_rows_than_decode_accepts`。

### 12. `Bind` 参数替换放大（DoS，已修）

`substitute_params` 把每个 `$n` 替换成参数文本，没有输出上限。实测 1000 个 `$1` 加 1000
字节参数产出 1,002,000 字节（放大 500 倍）；16 MiB 的 SQL（约 800 万个 `$1`）配 16 MiB
参数可以放大到 TB 级。

**修复**：替换输出上限 16 MiB，超限返回 `Protocol("substituted SQL exceeds ...")`。
**回归**：`security_tests::substitution_amplification_is_capped`。

### 13. prepared statement / portal 没有数量上限（DoS，已修）

每条连接用 `BTreeMap` 保存 prepared statement 与 portal，只有单条消息大小上限，没有条数
或累计字节上限；一条连接可以不停发 `Parse`/`Bind` 把 SQL 文本堆在内存里。

**修复**：prepared 最多 1024 条、累计 SQL 最多 16 MiB，portal 最多 1024 条，超限返回协议
错误。
**回归**：`security_tests::prepared_statement_count_is_capped`。

### 14. `COPY` 行数没有上限（DoS，已修）

`copy_in` / `copy_in_csv` / `copy_in_binary` 的 `inserted` 只增不减，客户端可以一直发
`CopyData`。

**修复**：一次 COPY 最多 `1 << 20` 行，超限回
`COPY inserts more than ... rows` 并结束 COPY。
**回归**：代码级修复，由表行上限一致的集成路径覆盖；socket 级长连接测试成本高，未单独加。

### 15. WAL 时间索引整文件读入（资源边界，已修）

`TimeIndex::open` 与 `lookup_time` 用 `read_to_end` 把 `<wal>.timeidx` 整个读入内存；损坏
或恶意文件可以直接耗尽内存。

**修复**：`MAX_TIME_INDEX_BYTES = 64 MiB`；`open` 超限时重建索引，`lookup_time` 超限时
视为索引缺失。

### 16. `IN` 列表的 O(values × rows) 扫描（CPU DoS，已修）

`expr IN (v1, ..., vn)` 每行线性扫描整个列表。实测 5000 行表上 1000 / 4000 / 16000 个
候选值分别耗时 64 / 255 / 1022 ms，严格按乘积增长；16 MiB 的查询消息可以放约 100 万个
值，配合 1M 行表就是 10^12 次比较。

**修复**：绑定阶段把"全常量且多于 8 个"的列表折叠为 `Expr::InSet`（`HashSet<Value>` +
类型标记），`eval` 每行 O(1)；`NULL` 候选与类型不匹配保持三值语义。同样输入从 1022 ms
降到 24.5 ms。
**回归**：`engine::tests::constant_in_list_keeps_null_semantics`。

### 17. 相关子查询逐行执行没有上限（CPU DoS，已修）

外层每一行都会重新执行一次相关子查询。实测 2000 × 2000 行耗时 896 ms；1M 行的外层表
会到小时级。

**修复**：`MAX_CORRELATED_ROWS = 10_000`，超过时返回
`Unsupported("correlated subquery would run for ... rows ...; rewrite it as a JOIN")`。
**回归**：`engine::tests::correlated_subquery_row_cap`。

### 18. `COPY` CSV 未闭合引号被静默接受（数据完整性，已修）

`parse_csv_line` 遇到没有闭合的引号时把行尾剩余内容当作字段值，列数恰好匹配时错误的
数据会被插进表里，没有任何提示。

**修复**：解析返回 `unterminated` 标记，`copy_in_csv` 回
`COPY CSV has an unterminated quoted field`；同时修正 `escape == quote` 时单个引号应
视为字段闭合（`""` 才是转义引号）。
**回归**：`security_tests::unterminated_csv_quotes_are_rejected`。

### 19. 存储层 fuzz 覆盖扩展（无新增崩溃）

原有 fuzz 只覆盖 `storage` / CAS / `format` / `radix` 解码器。补上：

- `page_view_parse_never_panics`：2000 轮随机 8 KiB 页 + 随机长度 `parse_slice`；
- `random_txn_snapshot_never_panics`：200 轮随机 `.snap`，强制 `TRSN` magic + version
  以命中 entry 解析器；
- `random_page_store_files_never_panic`：200 轮随机 data/WAL 文件走 `PageStore::open`
  的恢复路径（含尾部截断与 WAL 重放）。

6 个 fuzz 测试全绿，未发现新的 panic/abort；同时核验 snapshot 解析已有
`entry_count <= payload_len / 8`、payload 上限、长度与 CRC 校验。

### 20. CLI `graph knn` 点数上限（资源边界，已修）

`graph_knn` 直接调用 `annotated_knn`，而该函数没有点数上限（WAL 路径已经过
`decode_points` 的 `MAX_POINTS` 校验，但 `--points` 路径没有）。现在调用前校验
`points.len() <= MAX_POINTS`，超限给出明确错误。

## 发现但未修复（低危 / 设计取舍）

1. **SQL 注释中的占位符**：`substitute_params` 不识别 `--` / `/* */`，注释里的 `$1` 也会被
   替换。无害（注释内容不执行），但语义不精确；修它需要完整词法器，暂不做。
2. **`copy_literal` 的 f64 分支**：`1e999` 能通过 `parse::<f64>()`（得到 `inf`）从而原样
   拼接；项目 parser 只接受整数，会报语法错误，不构成注入。保留。
3. **`copy_quote` 不转义反斜杠**：`lexer::read_string` 不把 `\` 当转义符（只有 `''`），
   所以安全。已核验。
4. **`parse_copy` 拒绝带空格/引号的表名**：`"weird name"` 会被拒绝。这是安全取舍
   （COPY 不接受此类表名）；普通 SQL 路径仍可用。
5. **`parse_script` 多语句执行**是设计（脚本文件）；上面两个注入入口已堵住。
6. **查询执行本身不可中断**：`engine_lock_timeout` 只限制排队等锁，已经开始的慢查询
   仍会占满引擎；真正的取消需要引擎侧协作，暂不做（见「后续建议」）。

## 已核验安全（审计覆盖）

- `read_startup` 上限 1 MiB；`read_message` 上限 16 MiB；
- `tritdb-cas` 的 `Manifest::decode` / `Anchor::decode`：`checked_add`、`get`、trailing 检查；
- `tritdb-format` 的 `BlockView::decode`：长度、CRC32、padding 校验；
- `tritdb-wal` 的 `read_u32/u64`：越界返回错误；
- `tritdb-sql::storage` v6：chunk/row 计数、截断、类型、`NOT NULL` 校验；
- `tritdb-radix::unpack`：长度校验（`packed_len`）；
- `tritdb-page`：CRC32 + 半写检测；
- `tritdb-pgwire` 的 MD5 / 明文密码 / SCRAM 比较：统一 `constant_time_eq`（无提前返回）；
- `tritdb-pgwire` 的连接配额与引擎锁等待超时：`max_connections`、`engine_lock_timeout`；
- `tritdb-exec::graph`：节点/边/点/维度上限在构造（`from_edges`）与解码（`decode` /
  `decode_points`）两侧都校验；`annotated_knn` 的负数距离用 `i128` 精确计算；
- CLI 的 `parse::<usize>` / `parse_var_name`：都有 `map_err` 错误处理。
